# Bodyguard / Rectangular Ring Integration Plan

## Status

Implementation-ready plan. This document supersedes the earlier corner-targeting design.

## 1. Objective

When the normal bot enters a genuine movement cycle, switch persistently to `BodyguardRole`.

`BodyguardRole` has two phases:

1. **Entry phase**: use the existing navigation system to reach the first cell of a precomputed rectangular ring.
2. **Tracing phase**: once the head reaches that first ring cell, stop using navigation and follow the exact precomputed perimeter path, one step per turn.

The body should therefore trace a closed rectangular perimeter rather than repeatedly asking the navigation system for changing corner targets.

The existing plan establishes that `rect_adapter.hpp` bridges `Memory` to `bodyguard::rect::Snapshot`, that `rect_ring.hpp` provides `generate()`, `validate()`, `Box`, `Plan`, and `Snapshot`, and that `Snapshot` is large enough that it should have static storage duration rather than live on the WASM stack.

---

## 2. Important Corrections From the Previous Design

### 2.1 Do not advance the corner/path index every turn

The old design did this:

```cpp
Vec2 target = corners[corner_index % 4];
corner_index = (corner_index + 1) % 4;
```

That changes the target before the bot has reached it.

The corrected design only advances the perimeter index after the controller reports that the bot actually reached the expected cell.

### 2.2 A repeated position is not sufficient proof of a cycle

A position such as `(4, 4)` can be visited multiple times without the trajectory being periodic. Cycle detection should therefore look for a repeated sequence of positions, not merely one repeated coordinate.

### 2.3 Do not use four map corners as the ring

The ring is a rectangle selected/generated by the rectangular-ring subsystem. The four corners are only turning points of that rectangle.

### 2.4 Navigation is used only to enter the ring

`BodyguardRole` does **not** use `NavMode::Navigate` for perimeter tracing. Once the first ring cell is reached, the exact next cell is already known.

### 2.5 Do not build duplicate snapshots

Create one static `bodyguard::rect::Snapshot` for the Bodyguard geometry-generation work. Do not create one in `main.cpp` and another inside `BodyguardRole::act()` unless the real architecture proves that both are necessary.

# 3. Behavioral Model

The complete state machine is:

```text
             +----------------+
             | Normal role    |
             +-------+--------+
                     |
               cycle detected
                     |
                     v
             +---------------+
             | NeedRing       |
             +-------+-------+
                     |
          generate + validate ring
                     |
                     v
             +---------------+
             | EnteringRing   |
             +-------+-------+
                     |
              normal Navigate
                     |
          reach path[0]
                     |
                     v
             +---------------+
             | TracingRing    |
             +-------+-------+
                     |
             | exact next-cell |
             | direct movement |
             +-------+-------+
                     |
            repeat perimeter
                     |
                     +---------> path[0]
```

The critical invariant during tracing is:

```text
current head position == ring_path.cells[current_index]
```

At each turn:

1. Observe the actual current position.
2. Verify that it matches the expected ring cell.
3. Execute exactly one predefined move from that ring cell to the next ring cell.
4. Do not invoke the planner.
5. On the following turn, observe the new position and then advance the index.

# 5. Cycle Detection

## 5.1 Requirements

Use fixed-size storage only.

Keep the last 32 head positions. A cycle is detected only when a sequence of length `period` repeats twice consecutively. Test periods from 2 through 16.

For example:

```text
A B C A B C A B C
```

contains a period-3 cycle.

But:

```text
A B C B D
```

does not establish a cycle.

## 5.2 `cycle_detector.hpp`

```cpp
#pragma once

#include <array>

namespace bot {

class CycleDetector {
    static constexpr int HISTORY = 32;

    std::array<Vec2, HISTORY> history{};
    int size = 0;
    int write_pos = 0;

    static bool equal(const Vec2& a, const Vec2& b) {
        return a.x == b.x && a.y == b.y;
    }

    const Vec2& from_back(int offset) const {
        int idx = write_pos - 1 - offset;

        while (idx < 0) {
            idx += HISTORY;
        }

        return history[idx];
    }

public:
    void reset() {
        size = 0;
        write_pos = 0;
    }

    void push(const Vec2& position) {
        history[write_pos] = position;
        write_pos = (write_pos + 1) % HISTORY;

        if (size < HISTORY) {
            ++size;
        }
    }

    bool detect() const {
        for (int period = 2; period <= 16; ++period) {
            if (size < 2 * period) {
                continue;
            }

            bool repeated = true;

            for (int i = 0; i < period; ++i) {
                if (!equal(from_back(i), from_back(i + period))) {
                    repeated = false;
                    break;
                }
            }

            if (repeated) {
                return true;
            }
        }

        return false;
    }
};

}
```

### Why the bounds matter

Never compare against unused, zero-initialized history entries. Only the first `size` positions are valid observations.

This avoids the classic false positive where the initial head happens to be `(0, 0)`.

# 6. Exact Rectangular Perimeter Path

The navigation system is intentionally not responsible for perimeter tracing.

Represent the rectangle as an ordered list of every perimeter cell.

For:

```text
left   <= x <= right
 top   <= y <= bottom
```

the generated path is clockwise:

```text
(top-left) ----------------> (top-right)
                                |
                                |
                                v
(bottom-right) <-------------- (bottom-left)
```

## 6.1 `ring_path.hpp`

```cpp
#pragma once

#include <array>
#include <cassert>
#include <cstdlib>

namespace bot::roles {

enum class StepDir {
    Up,
    Right,
    Down,
    Left
};

struct RingBox {
    int left;
    int top;
    int right;
    int bottom;
};

struct RingPath {
    static constexpr int MAX_CELLS = 1024;

    std::array<Vec2, MAX_CELLS> cells{};
    std::array<StepDir, MAX_CELLS> moves{};
    int count = 0;

    bool push(const Vec2& cell) {
        if (count >= MAX_CELLS) {
            return false;
        }

        cells[count++] = cell;
        return true;
    }
};

inline StepDir direction_between(const Vec2& a, const Vec2& b) {
    const int dx = b.x - a.x;
    const int dy = b.y - a.y;

    assert(std::abs(dx) + std::abs(dy) == 1);

    if (dx == 1) {
        return StepDir::Right;
    }

    if (dx == -1) {
        return StepDir::Left;
    }

    if (dy == 1) {
        return StepDir::Down;
    }

    return StepDir::Up;
}

inline RingPath make_rectangular_ring(const RingBox& box) {
    RingPath path{};

    if (box.left >= box.right || box.top >= box.bottom) {
        return path;
    }

    for (int x = box.left; x <= box.right; ++x) {
        if (!path.push(Vec2{x, box.top})) {
            return RingPath{};
        }
    }

    for (int y = box.top + 1; y <= box.bottom; ++y) {
        if (!path.push(Vec2{box.right, y})) {
            return RingPath{};
        }
    }

    for (int x = box.right - 1; x >= box.left; --x) {
        if (!path.push(Vec2{x, box.bottom})) {
            return RingPath{};
        }
    }

    for (int y = box.bottom - 1; y > box.top; --y) {
        if (!path.push(Vec2{box.left, y})) {
            return RingPath{};
        }
    }

    for (int i = 0; i < path.count; ++i) {
        const int next = (i + 1) % path.count;
        path.moves[i] = direction_between(
            path.cells[i],
            path.cells[next]
        );
    }

    return path;
}

inline bool same_position(const Vec2& a, const Vec2& b) {
    return a.x == b.x && a.y == b.y;
}

inline RingPath rotate_path_to_start(
    const RingPath& original,
    const Vec2& start
) {
    RingPath result{};

    int start_index = -1;

    for (int i = 0; i < original.count; ++i) {
        if (same_position(original.cells[i], start)) {
            start_index = i;
            break;
        }
    }

    if (start_index == -1) {
        return result;
    }

    for (int i = 0; i < original.count; ++i) {
        const int src =
            (start_index + i) % original.count;

        result.cells[i] = original.cells[src];
        ++result.count;
    }

    for (int i = 0; i < result.count; ++i) {
        const int next = (i + 1) % result.count;

        result.moves[i] = direction_between(
            result.cells[i],
            result.cells[next]
        );
    }

    return result;
}

}
```

## 6.2 Perimeter size

For a `W x H` rectangle:

```text
perimeter = 2 * W + 2 * H - 4
```

Examples:

```text
3 x 3 ->  8 cells
4 x 4 -> 12 cells
5 x 5 -> 16 cells
6 x 6 -> 20 cells
```

If the body must occupy every perimeter cell simultaneously, the rectangle must satisfy the game's body-length requirement.

# 7. Ring Selection Using `rect_ring`

`rect_ring.hpp` remains the authority for deciding which rectangle is valid.

The flow should be:

```text
Memory
  |
  v
fill_snapshot()
  |
  v
rect_ring::generate()
  |
  v
rect_ring::validate()
  |
  v
validated Box
  |
  v
make_rectangular_ring()
  |
  v
RingPath
```

The exact function and field names must match the actual `rect_ring.hpp` implementation. Do not invent members that are not present in that header.

A conceptual helper is:

```cpp
        memory,
        round,
        snap

    // Replace this call with the exact existing rect_ring::generate()
    // signature from rect_ring.hpp.
    bodyguard::rect::Plan plan =
        /* bodyguard::rect::generate(snap, head, ...) */;

    // Replace this call with the exact existing validate() signature.
    if (!bodyguard::rect::validate(
            /* snap, plan, ... */)) {
        return false;
    }

    // Map the actual Plan/Box fields to RingBox here.
    RingBox box{
        /* plan.box.left   */,
        /* plan.box.top    */,
        /* plan.box.right  */,
        /* plan.box.bottom */
    };

    RingPath generated =
        make_rectangular_ring(box);

    if (generated.count == 0) {
        return false;
    }

    // Prefer to start tracing at the current head if the generated
    // rectangle already contains the head.
    RingPath rotated =
        rotate_path_to_start(generated, head);

    if (rotated.count == 0) {
        // The first square is not currently occupied by the head.
        // The caller should use normal Navigate mode to enter rotated[0]
        // once the desired starting point has been selected.
        path = generated;
        return true;
    }

    path = rotated;
    current_index = 0;
    return true;
}
```

### Important

The real implementation should select a **first ring cell** that is compatible with the normal navigation system and current body geometry. If the current head is not already on the perimeter, Bodyguard enters the ring using `Navigate` and only switches to exact path following after arrival.

# 8. Bodyguard State

Use three operational states:

```cpp
enum class BodyguardState {
    NeedRing,
    EnteringRing,
    Tracing
};
```

`Aborted` can be added if the surrounding code has a defined failure state, but it is not required for the basic design.

## State meanings

### `NeedRing`

Generate and validate the rectangle. Construct the complete perimeter path.

### `EnteringRing`

Use the existing navigation system:

```cpp
action.request.mode = NavMode::Navigate;
action.request.has_target = true;
action.request.target = path.cells[0];
```

The planner is allowed to choose how to reach the first ring cell.

### `Tracing`

The planner is completely bypassed. Execute:

```text
path.cells[current_index]
    ->
path.cells[current_index + 1]
```

using the precomputed direction.

```cpp
Action BodyguardRole::act(
    const unswbc::Controller& controller,
    const Memory& memory,
    const nav::Grid& grid,
    const comms::Inbox& inbox
) {
    (void)grid;
    (void)inbox;

    Action action{};

    // -------------------------
    // Phase 1: build the ring
    // -------------------------
    if (state == BodyguardState::NeedRing) {
        const int round = memory.current_round;

        if (!build_ring(controller, memory, round)) {
            return action;
        }

        // The first ring cell is path.cells[0].
        if (same_position(
                controller.get_position(),
                path.cells[0])) {
            current_index = 0;
            state = BodyguardState::Tracing;
        } else {
            state = BodyguardState::EnteringRing;
        }
    }

    // --------------------------------
    // Phase 2: enter the ring normally
    // --------------------------------
    if (state == BodyguardState::EnteringRing) {
        const Vec2 current = controller.get_position();
        const Vec2 first = path.cells[0];

        if (same_position(current, first)) {
            current_index = 0;
            state = BodyguardState::Tracing;
        } else {
            action.request.mode = NavMode::Navigate;
            action.request.has_target = true;
            action.request.target = first;
            return action;
        }
    }

    // ---------------------------------
    // Phase 3: exact perimeter tracing
    // ---------------------------------
    if (state == BodyguardState::Tracing) {
        const Vec2 current = controller.get_position();
        const Vec2 expected = path.cells[current_index];

        if (!same_position(current, expected)) {
            // The actual position diverged from the predetermined path.
            // Rebuilding the ring is safer than silently invoking Navigate.
            state = BodyguardState::NeedRing;
            return Action{};
        }

        const int next_index =
            (current_index + 1) % path.count;

        action.request.mode = NavMode::Direct;
        action.request.has_target = false;
        action.request.direct_direction =
            path.moves[current_index];

        // Do not advance `current_index` here.
        // The index advances only after the next turn confirms that the
        // controller actually arrived at path[next_index].
        return action;
    }

    return action;
}

Role& bodyguard_role() {
    static BodyguardRole role;
    return role;
}

}
```

### One correction to the above control skeleton

The exact index update must happen on the **next observed state**, not immediately after the action is returned.

The production version should therefore do:

```cpp
const Vec2 current = controller.get_position();
const Vec2 expected = path.cells[current_index];

if (!same_position(current, expected)) {
    const int next_index =
        (current_index + 1) % path.count;

    if (same_position(current, path.cells[next_index])) {
        current_index = next_index;
    } else {
        state = BodyguardState::NeedRing;
        return Action{};
    }
}

Action action{};
action.request.mode = NavMode::Direct;
action.request.has_target = false;
action.request.direct_direction =
    path.moves[current_index];

return action;
```

This preserves the invariant that state reflects **observed reality**, not an assumed successful movement.

# 13. Main Loop Integration

The cycle detector belongs in `main.cpp`.

State:

```cpp
bot::CycleDetector cycle_detector;
bool cycle_detected = false;
```

Per turn:

```cpp
while (game_running) {
    memory.update(...);

    tracker.reconcile(...);

    const Vec2 head = controller.get_position();

    if (!cycle_detected) {
        cycle_detector.push(head);

        if (cycle_detector.detect()) {
            cycle_detected = true;
        }
    }

    bot::roles::Role& role =
        cycle_detected
            ? bot::roles::bodyguard_role()
            : bot::roles::select_role();

    Action action = role.act(
        controller,
        memory,
        grid,
        inbox
    );

    execute_turn(
        controller,
        memory,
        action
    );
}
```

Keep the transition persistent unless the game architecture explicitly requires returning to the previous role.

# 14. Ring Entry Semantics

The selected ring has a distinguished first cell:

```cpp
path.cells[0]
```

The bot uses existing navigation only for this step:

```cpp
action.request.mode = NavMode::Navigate;
action.request.has_target = true;
action.request.target = path.cells[0];
```

The role must remain in `EnteringRing` until:

```cpp
controller.get_position() == path.cells[0]
```

At that exact moment:

```cpp
state = BodyguardState::Tracing;
current_index = 0;
```

The next action is the first predefined perimeter move.

This prevents a planner-generated path from becoming part of the ring itself.

# 15. Exact Perimeter Tracing

Suppose the generated path is:

```text
(2,2) -> (3,2) -> (4,2) -> (5,2)
(5,3) -> (5,4) -> (5,5)
(4,5) -> (3,5) -> (2,5)
(2,4) -> (2,3) -> (2,2)
```

The action sequence is exactly:

```text
RIGHT
RIGHT
RIGHT
DOWN
DOWN
LEFT
LEFT
LEFT
UP
UP
```

followed by the closing move:

```text
UP
```

The planner is never consulted while executing these moves.

# 16. Closing the Ring

The last path cell has a predefined move back to the first cell:

```cpp
path.moves[path.count - 1]
```

That move must only be executed when the game's collision/body update rules permit the head to enter the first perimeter cell.

This needs to be verified from the actual movement/collision implementation.

If the tail vacates before collision resolution, a completely closed loop is possible.

If collision is checked against the pre-move body, the final closure move may be illegal. In that case the implementation should either:

- maintain a one-cell opening, or
- generate a rectangle whose semantics are known to permit closure.

Do not assume closure is legal without checking the engine rules.

# 17. Validation Before Tracing

Before entering `Tracing`, validate all of the following:

```cpp
path.count >= 4
```

```cpp
path.cells[0] == controller.get_position()
```

```cpp
for every i:
    Manhattan(path.cells[i], path.cells[(i+1)%path.count]) == 1
```

and, where required by the game:

```cpp
body_length >= path.count
```

The rectangle generator/validator should also reject blocked or otherwise invalid perimeter cells.

# 18. Handling Divergence

If the bot is supposed to be tracing:

```text
expected = path[current_index]
```

but the observed head is somewhere else, do not silently switch back to normal navigation.

Use:

```cpp
state = BodyguardState::NeedRing;
```

and regenerate the rectangle from a fresh snapshot.

A divergence can happen because of:

- an illegal direct movement being rejected,
- an external game event modifying position,
- a changed board state,
- a collision,
- a portal/teleport event, if the game allows it.

The invariant should always be restored before tracing resumes.

# 24. Performance

The design remains fixed-size and deterministic.

Cycle detection:

```text
O(16 * 16) per turn at worst
```

Ring generation:

```text
O(perimeter)
```

Path following:

```text
O(1) per turn
```

No dynamic allocation is required for:

- cycle history,
- ring cells,
- ring moves,
- rectangle state.

The expensive planner is used only while entering the first ring cell.

# 25. Correctness Invariants

The implementation should maintain these invariants.

### Invariant 1 — cycle detector

Only observed positions are compared; unused history slots are ignored.

### Invariant 2 — ring path

Every consecutive pair of path cells differs by exactly one Manhattan step.

### Invariant 3 — tracing index

`current_index` refers to the last path cell confirmed by actual observation.

### Invariant 4 — tracing movement

The action issued from `path[current_index]` is exactly `path.moves[current_index]`.

### Invariant 5 — no planner during tracing

`BodyguardState::Tracing` never produces `NavMode::Navigate`.

### Invariant 6 — entry

`EnteringRing` ends only after the controller actually reaches `path.cells[0]`.

### Invariant 7 — failure

If observed position differs from both the current and next expected ring cells, the ring is invalidated and must be rebuilt.

# 29. Final Implementation Rules

1. Detect a real repeated trajectory, not merely a repeated position.
2. Generate the rectangle through the existing `rect_ring` system.
3. Validate the rectangle before using it.
4. Choose a distinguished first perimeter cell.
5. Use the existing navigation system only until the head reaches that first cell.
6. Once there, switch to exact predefined path following.
7. Never invoke the planner during perimeter tracing.
8. Advance the path index only after observing the move actually succeeded.
9. Rebuild the ring if the observed head diverges from the expected path.
10. Keep large snapshots static.
11. Keep all ring/path/cycle state fixed-size and deterministic.
12. Verify the game's body-collision semantics before enabling the final closure move.
